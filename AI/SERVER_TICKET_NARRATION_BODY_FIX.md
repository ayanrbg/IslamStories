# Серверу: пустое тело `/narrate` — причина найдена, что нужно с вашей стороны

Ответ на ваш тикет «`SerializeObject` отдаёт `{}` на устройстве». Диагноз верный,
на клиенте исправлено. Ниже — что именно, как проверить и три просьбы.

## Причина подтверждена

Тело собиралось из **анонимного типа**. Newtonsoft сериализует его рефлексией, а
IL2CPP managed stripping выбрасывает метаданные типа, на который больше никто не
ссылается: полей не остаётся, `JsonConvert` отдаёт `{}`. Молча, без исключения, и
**только на устройстве** — в редакторе (Mono, без стриппинга) тот же код работает,
поэтому дефект пережил всю отладку.

Ваше наблюдение «`narrate-all` работает, `narrate` нет» было ключом: `narrate-all`
всегда собирался из обычного класса `NarrateAllPayload`, поэтому стриппинг его не
трогал.

## Что сделано на клиенте (сборка 2.7)

Ваш вариант 1 — именованный класс:

```csharp
[Serializable]
[UnityEngine.Scripting.Preserve]
public class NarratePayload
{
    public string text;
    public string narratorGender;
    public string name;
    public string gender;
}

var body = JsonConvert.SerializeObject(new NarratePayload {
    text           = text,
    narratorGender = Narrator(narratorGender),
    name           = Name(),
    gender         = UserProfile.ChildGender,
}, new JsonSerializerSettings { NullValueHandling = NullValueHandling.Ignore });
```

Плюс `Assets/link.xml`, сохраняющий весь `FairyTales.Models`, — чтобы это не
вернулось при повышении уровня стриппинга. `Newtonsoft.Json` целиком в
`preserve="all"` заворачивать не стали: это заметный вес в билде, а корень был в
метаданных наших типов, не библиотеки. Если после 2.7 тело всё равно окажется
коротким — расширим.

Проверено по всей кодовой базе: анонимных типов в JSON-телах больше **нет ни одного**,
в обоих проектах (Bala и Islam Stories).

## Просьба 1 — не поднимайте `narrationEpoch`, пока 2.7 не разойдётся

Эпоха сейчас `2`, и она отработала — видно в нашем же событии (`epoch=2; purged=1`),
спасибо. Но следующий бамп имеет смысл только после того, как 2.7 разойдётся по
устройствам: клиент запоминает увиденное число, и повторный бамп на ту же величину
уже ничего не сделает. Поднимете раньше — потратите TTS впустую и потеряете рычаг.

## Просьба 2 — поле `narrationQuiet` в конфиге

Клиент 2.7 логирует **каждый** запрос озвучки: `narrate_request` + `narrate_response`,
то есть ~100 событий на книгу в 49 страниц, каждое отдельным POST. Для разбора
инцидента это то, что нужно, дальше — лишний трафик.

Добавьте в ответ `GET /api/debug/config` (и в тело ответа `POST /api/debug/logs`):

```jsonc
{
  "hasConfig": true,
  "narrationEpoch": 2,
  "defaultNarratorGender": "male",
  "narrationQuiet": true    // ← новое: выключает поштучное логирование озвучки
}
```

**Поле инвертировано намеренно.** `JsonUtility` в Unity не отличает отсутствующий
`bool` от `false`, поэтому «нет поля» обязано означать «логировать»: иначе первый же
билд после любой правки окажется немым ровно тогда, когда логи нужнее всего.
Семантика: `narrationQuiet: true` — молчать, поле отсутствует или `false` — писать.

Клиент уже умеет это читать, применять и хранить между запусками. Пока сервер поля
не отдаёт, логирование включено — это ожидаемое поведение, а не ошибка.

## Просьба 3 — придержите `ADMIN_KEY` под рукой

Читать `/api/debug/log` без него нельзя (401), а именно там лежит ответ на вопрос
«клиент или сервер». Достаточно одного ключа на команду — сейчас каждый разбор
упирается в то, что клиентская сторона свои же логи прочитать не может.

## Приёмка 2.7

| Что смотреть | Было | Ожидается |
|---|---|---|
| `narrate_request` → `bodyLen` | `2` | ≈ `textLen + 60…80` |
| Ваш лог → `clen` | `2` | то же число, что `bodyLen` |
| `X-Narrator-Gender-Source` | `config-fallback` | `request` |
| `X-Narrator-Gender` | `male` всегда | совпадает с нажатой кнопкой |
| Строки «пол диктора не распознан» со `сборка=2.7` | есть | нет |

Строки со сборками **2.0–2.6 останутся** — там дефект в самом билде, и вылечит их
только обновление у пользователей. Фильтруйте по версии, иначе картина будет
выглядеть неисправленной ещё недели две.

## Про Android — уточнение к вашей просьбе

Собрать Android 2.6 для сравнения можно, но результат надо читать осторожно: под
IL2CPP он поведёт себя **так же**, как iOS, — стриппинг тот же, разница лишь в
бэкенде компиляции. Пустое тело там будет ровно по той же причине. Разница появится
только если Android собирается под Mono — тогда тело окажется нормальным и до правки.
То есть тест разделяет не «iOS против Android», а «IL2CPP против Mono».
